# 013 — WSDL folder-drop → DSL generation

## Filed

2026-07-28 initial filing; revised across 2026-07-28 and
2026-07-29 into five shapes as Rainer clarified intent. The
design journey (kept here so future readers see why the final
shape is what it is):

| v | Shape | Dropped because |
|---|---|---|
| 1 | CLI scaffold — one-shot dev tool | Too dev-tool-y; doesn't solve the operator persona |
| 2 | Boot-time runtime auto-gen with cache + refresh | Too much magic + cold-start cost + refresh complexity |
| 3 | CI-driven pre-generation with drift detect | Operator-hostile: CI setup + PR cycle per new service |
| 4 | XTR-native w/ folder drop + gated admin URL endpoint | Admin URL endpoint conflates threat models with infra-level controls; ops already separates admin from consumer surfaces |
| 5 | **Folder drop only (this)** | Simplest thing that works. Localhost dev = zero friction, prod = ops mounts WSDLs via config-management, no in-process admin surface to secure. |

## Severity

**High** for adoption. Zero setup friction, zero in-process
attack surface, matches how config-management (Ansible,
Kubernetes ConfigMap, systemd drop-ins) already delivers
files to running services.

## Design

### Config

One new `xtr.yaml` field, optional and off-by-default:

```yaml
# WSDL folder-drop. Operator places WSDL files here; XTR
# generates DSLs to `dsl_path:` at boot. Absent = feature off.
wsdl_watch_dir: /app/wsdl
```

That's it. No admin section. No API key. Access to
`wsdl_watch_dir` is filesystem-level access, same trust
boundary as edits to `xtr.yaml` itself. If ops wants a URL-
driven "add a service" workflow, they run `curl -o
<path>/foo.wsdl <url>` from a config-management job — that's
infra-level plumbing, not an XTR feature.

### Folder layout

Inside `wsdl_watch_dir`:

```
<wsdl_watch_dir>/
├── ar/                     # group name = subdir name
│   └── ariregister.wsdl    # any .wsdl file in the subdir
└── xroad/
    └── meta.wsdl
```

Boot-time flow per WSDL:

1. Parse WSDL via a new `src/wsdl/` module (see below).
2. Emit one DSL per `wsdl:operation` at
   `<dsl_path>/<group>/<operation>.yml`.
3. Each generated file leads with a marker header:
   ```yaml
   # GENERATED FROM wsdl/<group>/<file>.wsdl
   # Do not edit — regenerate by replacing the source WSDL
   # and restarting XTR. Delete this header to convert this
   # file into a hand-written override.
   ```
4. Collision rules on the DSL file:
   - File exists AND has the marker → overwrite (safe, we own
     it).
   - File exists WITHOUT the marker → SKIP with WARN
     ("hand-written override wins"). Operator's edits stand.
   - File doesn't exist → write.

Existing `loader::load_all` then picks up every generated +
hand-written `.yml` unchanged. Zero changes to loader
behaviour.

### Reload posture

**v1 (this task):** boot-time only. Drop/change/remove a
WSDL → restart XTR → DSL set matches the WSDLs on disk.

**v2 (follow-up task):** file-watcher on `wsdl_watch_dir`
via `notify` crate. On WSDL change → regenerate DSLs → hot-
swap `ServiceMap` atomically. Also add a "generated by our
own generator" dedupe check so the watcher doesn't loop on
our own writes.

v1 is a strict subset of v2's design — v2 adds the watcher
on top without changing v1's data flow.

### WSDL parser

New crate module `src/wsdl/` — runtime code, not a separate
crate.

Uses existing `quick-xml` dep — no new dependencies. Parses
the SOAP-1.1-over-HTTP subset X-Road uses:

- `wsdl:definitions` root
- `wsdl:types` → `xsd:schema` → element definitions
- `wsdl:message` → parts referencing types
- `wsdl:portType` → operations mapping input/output messages
- `wsdl:binding` → SOAP-over-HTTP binding, `soap:operation`
  soapAction
- `wsdl:service` → `soap:address location="..."` for the
  target URL

Unsupported constructs (WSDL 2.0, RPC/encoded, MIME
attachments, WS-Addressing headers beyond the X-Road ones) →
bail with a clear error naming the construct + the WSDL
file. Never emit a wrong DSL silently.

X-Road-specific envelope wrapping: when a sidecar
`<wsdl>.meta.yaml` sits next to the WSDL and provides
`{ member_class, member_code, subsystem_code, service_code }`,
the generator injects the standard X-Road header block
(`{{{generate.client}}}`, `{{generate.uuid}}`,
`{{generate.protocol_version}}`, `<xroad:service>` with
subsystem identity) into the envelope. Absent sidecar →
plain SOAP envelope (works for Ariregister-style public
HTTPS; needs a hand-written override for real X-Road
without the sidecar).

### Deterministic output

Generated YAML must be byte-stable across runs (same WSDL →
same DSL bytes):
- Fields in fixed order: `# marker`, `params:`, `service:`,
  `method:`, `envelope:`.
- Params in WSDL declaration order.
- Handlebars whitespace normalized.
- Trailing newline, LF line endings.

Enables the operator to `git diff` two runs and see only
what actually changed in the WSDL.

## Acceptance

- Configuring `wsdl_watch_dir` in `xtr.yaml` and dropping a
  WSDL under it makes the corresponding endpoints appear on
  next boot.
- Generated DSLs land at
  `<dsl_path>/<group>/<operation>.yml` with the marker
  header.
- Hand-written DSLs (no marker) survive when a WSDL would
  overwrite the same path — WARN log identifies the
  shadowing.
- Deleting a WSDL from `wsdl_watch_dir` + restarting removes
  the corresponding generated DSLs (only ones carrying the
  marker; hand-written stays).
- Existing tests unchanged (loader/handlebars/executor path
  is untouched).
- Round-trip test: drop
  `tests/fixtures/wsdl/ariregister.wsdl` (a captured copy of
  the public WSDL) into a temp `wsdl_watch_dir`; boot XTR;
  assert the 4 generated `/ar/*` endpoints exist and their
  envelopes contain the expected `<prod:*>` operation
  elements + the params from the input message.
- Determinism test: run the generator twice against the
  same WSDL; assert byte-equal outputs both times.
- Malformed / unsupported WSDL → clear startup error naming
  the file + the construct that failed. XTR still boots with
  whatever other DSLs succeeded.
- New `book/src/ops/wsdl-ingestion.md` chapter documents
  folder layout, marker semantics, override rules,
  X-Road sidecar convention.
- `book/src/dsl/adding-a-service.md` "Coming soon" section
  becomes past-tense.
- `SUMMARY.md` gains the new chapter link.

Total: **~4 days** of focused work.

## Dependencies

- None. `notify` crate for v2 hot-reload but not v1.

## Non-scope

- **Admin/management HTTP endpoint.** Explicitly rejected in
  v5 — admin/consumer surfaces stay hard-separated at the
  infra layer, not baked into XTR. If ops needs URL-driven
  WSDL ingestion, they run `curl -o
  <wsdl_watch_dir>/<file>.wsdl <url>` from
  config-management.
- **Hot-reload on WSDL change.** v2 follow-up.
- **Multi-WSDL merging within a group** (multiple `.wsdl`
  files in same subdir). v1: each generates independently;
  operation-name collisions → last-loaded wins with WARN. A
  cleaner merge is a follow-up.
- **WSDL 2.0.** Not used in X-Road.
- **Version-controlling generated DSLs.** Operator's choice —
  the marker header makes them obviously auto-generated.
  Committing captures the current WSDL's state; not
  committing keeps the WSDL as the source of truth.
- **Fetching WSDLs from URLs.** Explicitly rejected — ops
  handles this before the file lands in `wsdl_watch_dir`.

## Risks

- **Generator determinism bugs**. Round-trip test asserts
  byte-equal output across two consecutive runs in CI.
- **WSDL parsing surprises in the wild**. Bail-out-on-
  unsupported-construct posture — never emit a wrong DSL.
  Operator overrides with hand-written for unsupported
  cases.
- **Filesystem sequencing** (generator writing while loader
  reading). v1 sequences them strictly: generate → then
  load. No concurrent access at boot. v2's hot-reload needs
  atomic file replace (`write to .tmp → rename`).
