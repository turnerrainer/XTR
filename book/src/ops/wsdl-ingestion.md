# WSDL folder-drop

Point XTR at a folder of WSDL files, restart, and every
`wsdl:operation` becomes a live REST endpoint. Task 013 v5.

## Enable it

Add one line to `xtr.yaml`:

```yaml
wsdl_watch_dir: /app/wsdl
```

Absent = feature off, XTR only serves hand-written DSLs from
`dsl_path`.

## Folder layout

Inside `wsdl_watch_dir`, one subdirectory per URL group; each
subdirectory contains one or more `*.wsdl` files:

```
/app/wsdl/
├── ar/
│   └── ariregister.wsdl        → POST /ar/<operation>
└── xroad/
    └── meta.wsdl               → POST /xroad/<operation>
```

XTR scans this tree at boot, parses each WSDL, and writes one
DSL per operation to `<dsl_path>/<group>/<operation>.yml`.

## Generated files carry a marker

Every generated `.yml` starts with a marker comment:

```
# GENERATED BY XTR from WSDL — do not edit; delete this line to convert into a hand-written override
```

That marker is how XTR decides who owns the file on the next
boot:

| File state | What XTR does |
|---|---|
| Doesn't exist | Write generated content |
| Exists, has marker | Overwrite with fresh generated content |
| Exists, no marker (hand-written) | SKIP with WARN — your edits stand |

Delete the marker line from a generated file and it becomes a
hand-written override. From that point on, XTR will never
touch it, and re-generation from the source WSDL is silently
skipped for that operation with a WARN log identifying the
shadowing.

## X-Road envelope wrapping (optional sidecar)

By default the generator emits a plain SOAP envelope pointing
at the WSDL's `<soap:address location="…"/>` — perfect for
public HTTPS services like Ariregister.

For X-Road services (mTLS via your Security Server), drop a
sidecar next to the WSDL:

`/app/wsdl/xroad/eesti-post.meta.yaml`:

```yaml
member_class: COM
member_code: "10328093"
subsystem_code: eesti-post-svc
# Optional — defaults to the operation name.
# service_code: trackParcel
```

When the sidecar is present, the generator injects the standard
X-Road header block (`{{{generate.client}}}`,
`{{generate.uuid}}`, `{{generate.protocol_version}}`,
`<xroad:service>` with the subsystem identity) into every
envelope generated from that WSDL. The Security Server routing
then uses the mTLS path described in
[X-Road Security Server setup](./xroad-security-server.md).

## What the generator supports

SOAP 1.1 document/literal binding — the flavour X-Road actually
uses. Specifically:

- `wsdl:definitions` with a `targetNamespace`
- `wsdl:types` → `xsd:schema` → inline `xsd:element` definitions
- `xsd:complexType` / `xsd:sequence` — recursed
- Nested wrapper elements (Ariregister's `<keha>` pattern) —
  flattened at scalar leaves for the params list
- `wsdl:message` / `wsdl:portType` / `wsdl:service` with
  `<soap:address location="…"/>`
- `xsd:element ... minOccurs="0"` — flagged as optional (used
  later in the OpenAPI generator; params list still includes
  them)

Explicitly rejected — the generator refuses to boot the
offending WSDL and logs a WARN naming the construct:

- `xsd:choice` — the generator can't guess which alternative
  the caller wants
- `xsd:import` — cross-schema references, out of scope for v1
- Named top-level `xsd:complexType` referenced by name — out
  of scope for v1
- WSDL 2.0 — nobody in the X-Road ecosystem uses it
- RPC/encoded — deprecated SOAP style

For any of these, override with a hand-written DSL (see
[Adding a new service](../dsl/adding-a-service.md)).

## Deterministic output

The generator emits byte-stable YAML — the same WSDL always
produces the same file. If you commit generated DSLs to git,
`git diff` between two runs only shows what changed in the
source WSDL. If you don't commit them, the WSDL is the source
of truth and XTR just regenerates on each boot.

## Failure modes

The generator NEVER blocks XTR from booting. Failures on one
WSDL only skip that WSDL's operations — every other WSDL still
ingests, every hand-written DSL still loads.

| Symptom | Cause | Fix |
|---|---|---|
| Boot log `WSDL ... failed to ingest: ... — skipping` | WSDL is malformed, references an undefined element, or uses an unsupported construct | Read the message — most cases say exactly which construct broke. Fix the WSDL or override with hand-written DSL |
| Boot log `hand-written override at ... shadows generated DSL` | You have a `.yml` at the same path that lacks the marker | Either accept the override (do nothing) or delete the hand-written file so the generator can take over |
| Endpoint 404 after WSDL drop | Restart XTR — v1 is boot-only. Hot reload is a v2 follow-up |
| Wrong param names in the envelope | Generator uses the WSDL's XSD element names as-is; if callers expect friendlier aliases (`reg_code` vs `ariregistri_kood`), override with a hand-written DSL |

## Why no admin HTTP endpoint

There's no `POST /admin/wsdl-from-url` or similar. The
management surface stays out of XTR:

- **Localhost dev**: `cp foo.wsdl /app/wsdl/mygroup/` +
  restart. Zero friction.
- **Production**: your config-management layer (Ansible,
  Kubernetes ConfigMap, systemd drop-in) delivers files. If
  you need URL-driven ingestion, run `curl -o
  /app/wsdl/foo.wsdl <url>` from that layer.

Admin and consumer surfaces stay hard-separated at the
infrastructure level, not muddled together via in-process auth.
